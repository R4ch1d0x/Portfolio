#01

Why enumerate after access

Getting a shell is rarely the end goal. Whether access came from a critical RCE or a low-privileged account, the next step is always the same: understand the box before trying to escalate. Unlike a CTF, a real engagement doesn't stop at initial access — enumeration keeps mattering through post-compromise.

What you're looking for

Kernel and OS version (known exploits), misconfigured permissions (SUID, writable files, sudo rules), credentials left in files or history, and anything that runs with higher privileges than the account running it.

Order of operations

Identify the system first, then the user context, then look for specific escalation primitives (SUID, sudo, cron, writable PATH). Broad before narrow.

For authorized testing and CTF practice (HTB/THM) only. Running these against systems you don't own or have written permission to test is illegal.

OS enumeration

Identify the kernel, distro and version to spot known exploits.

#02

hostname

Prints the machine's hostname. It can be a meaningless default (ubuntu-3487) or a naming-convention hint about the box's role (sql-prod-01, web-dmz-2), which is useful for mapping a network during a larger engagement.

Check the hostname

hostname
#03

uname -a

Prints kernel name, version, architecture and build date in one line. The kernel version is the first thing to check against known kernel exploits (Dirty COW, Dirty Pipe, PwnKit-adjacent kernel bugs, etc.).

Full kernel/OS banner

uname -a
# or individually:
uname -r   # kernel release
uname -m   # architecture

Cross-reference the kernel version with searchsploit or a CVE database before trying a kernel exploit — a wrong match can crash the box.

#04

/proc/version

The proc filesystem exposes live kernel and process information as regular files. /proc/version gives the kernel version plus the compiler (often GCC) used to build it — useful when you need to compile a local exploit and must match the target's toolchain.

Read it directly

cat /proc/version
#05

/etc/issue

A plain-text file meant to be shown before login, usually naming the distro and version. Like any banner file it can be edited or stripped, so treat it as a hint, not a guarantee — cross-check with uname -a and /etc/os-release.

Read it

cat /etc/issue
cat /etc/os-release

User enumeration

Identify who you are, what you can run, and who else exists on the box.

#06

ps and ps aux

Lists running processes. Plain ps only shows processes tied to the current terminal. ps aux shows every process for every user: all processes, include the user that launched each one, and processes not attached to a terminal (x). Look for services running as root that a low-privileged user can interact with or restart.

Process listing

ps              # current shell only
ps -A           # every process
ps axjf         # process tree
ps aux          # all users, with owner column
ColumnMeaning
PIDUnique process ID.
TTYTerminal type attached to the process, if any.
TIMECPU time used, not wall-clock runtime.
CMDThe executable's name — command-line arguments are not shown here.
#07

id

Shows the current user's UID, GID and all group memberships. Group membership matters: being in docker, lxd, disk or adm can each be its own privilege-escalation path even without any sudo rights.

Current and another user

id
id www-data   # check another account's UID/groups
#08

env

Lists environment variables for the current shell. PATH is the one to check first: if it includes a directory the current user can write to, and a root-run script or SUID binary calls a command without an absolute path, that's a PATH hijack. Also check for stray credentials left in variables.

List environment variables

env
echo $PATH
#09

sudo -l

Lists the commands the current user is allowed to run with sudo, with or without a password. Any binary listed here that can read files, write files, or spawn a shell (check GTFOBins for the specific binary) is a direct path to root.

List sudo rights

sudo -l

A command allowed with NOPASSWD is the most interesting entry — no credential needed, just the right GTFOBins technique for that binary.

#10

/etc/passwd

Readable by everyone by default, it lists every account on the system: username, UID, GID, home directory and login shell. Most entries are system or service accounts with no login shell — real human accounts are the ones worth targeting for credential reuse or lateral movement.

Filter to real users

cat /etc/passwd
grep home /etc/passwd          # accounts with a /home directory
cut -d: -f1 /etc/passwd         # usernames only, for a wordlist

If /etc/passwd is ever writable, that alone is a privilege-escalation path: appending a new root UID-0 entry with a known password hash creates a new root account.

#11

history

Shows the current shell's command history, and files like ~/.bash_history keep it across sessions. Admins sometimes type passwords or sensitive flags directly on the command line by mistake, so this is worth a quick scan even though hits are rare.

Current and saved history

history
cat ~/.bash_history
cat /root/.bash_history   2>/dev/null

Network enumeration

Find interfaces, routes and listening services that aren't visible from outside.

#12

ifconfig and ip route

Shows network interfaces. A box with more than one interface (e.g. eth0 plus a tun/internal interface) may be a pivot point into a network segment you can't reach directly. ip route confirms which routes actually exist from this host.

Interfaces and routes

ifconfig -a
ip a
ip route
#13

netstat

Shows existing connections and listening ports — useful for finding internal-only services (e.g. a database or admin panel bound to 127.0.0.1) that aren't visible from an external scan but can be reached locally.

Common flag combinations

netstat -a      # all listening + established
netstat -at     # TCP only
netstat -au     # UDP only
netstat -l      # listening only
netstat -s      # per-protocol statistics
netstat -tp     # TCP with service name and PID (needs root to see others' PIDs)
netstat -ano    # all sockets, no name resolution, timers

Files enumeration

Find SUID binaries, writable paths, and scheduled jobs a privileged process trusts.

#14

find -perm 4000 (SUID)

The SUID bit makes a binary run with its owner's privileges rather than the privileges of whoever executes it. A SUID binary owned by root that lets you read files, write files, or spawn a shell is a direct escalation path — check any hit against GTFOBins.

Find SUID binaries

find / -perm -u=s -type f 2>/dev/null
find / -perm -4000 -type f 2>/dev/null
# SGID equivalent (runs as the owning group):
find / -perm -g=s -type f 2>/dev/null

Redirecting errors to /dev/null keeps the output readable — find / generates a lot of "Permission denied" noise on a real filesystem.

#15

Writable and executable paths

Beyond SUID, a world-writable directory that a privileged process reads from (a script run by cron, a service's config, a library path) is just as useful — drop or replace a file there and wait for it to run as someone else.

Write access

Three equivalent ways to find world-writable directories; the manual page explains why there are three flag styles for one permission check.

Execute access

World-executable directories and the presence of a compiler or scripting runtime, which matters if you need to build or run a local exploit on-box.

Writable / executable / toolchain checks

find / -writable -type d 2>/dev/null
find / -perm -222 -type d 2>/dev/null
find / -perm -o w -type d 2>/dev/null

find / -perm -o x -type d 2>/dev/null    # world-executable dirs

find / -name "python*" 2>/dev/null
find / -name "perl*" 2>/dev/null
find / -name "gcc*" 2>/dev/null
#16

Cron jobs

Scheduled tasks often run as root. If a cron job calls a script that your current user can edit, or a script with no absolute paths that relies on a writable PATH entry, you can get code to run as whoever owns the cron job — usually root.

Where cron jobs are defined

cat /etc/crontab
ls -la /etc/cron.d/ /etc/cron.daily/ /etc/cron.hourly/
crontab -l                 # current user's own jobs
crontab -l -u root 2>/dev/null
cat /var/spool/cron/crontabs/* 2>/dev/null

Check the permissions on every script a cron job references, not just the crontab file itself — the crontab can be read-only while the script it calls is writable.

#17

Methodology checklist

A repeatable order to run through on a fresh shell, roughly matching the sections above.

  1. Identify the system — hostname, uname -a, /proc/version, /etc/issue.
  2. Identify the user context — id, env, sudo -l.
  3. Look around — ps aux, /etc/passwd, history, ls -la on home directories (hidden files are easy to miss with plain ls).
  4. Network context — ifconfig / ip a, ip route, netstat -ano.
  5. Escalation primitives — SUID/SGID binaries, writable files/directories a privileged process touches, cron jobs.
  6. Cross-reference — kernel version against CVEs, SUID binaries against GTFOBins, sudo rules against GTFOBins.

Key takeaways

  • Enumeration doesn't stop at initial access — it's the main activity of the post-compromise phase.
  • Check broad system facts first (kernel, OS), then user context (id, sudo), then specific primitives (SUID, cron, writable paths).
  • Most privesc paths are misconfigurations — excess sudo rights, a writable file a root process trusts, a SUID binary that shouldn't exist — not kernel exploits.

Use only on systems you own or are authorized to test (HTB, THM, or your own labs).
