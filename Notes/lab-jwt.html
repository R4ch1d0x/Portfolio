JWT Forgery

A JSON Web Token is only as trustworthy as the secret that signs it. In my Safe Shelter Connect audit the secret was hardcoded, so anyone who found it could mint their own admin token. This lab replays that finding against a fictional app, then shows the fix.

Everything here is simulated in your browser. The app, users and secret are invented. No request leaves this page.

Server of "ShelterDesk" (fictional)
01

Log in as a normal volunteer

The server answers a login with a signed token. The browser sends it back on every request. Header and payload are only Base64 encoded, so anyone can read them. The signature stops edits.

02

Find the secret

Secrets end up in repositories, front-end bundles, backups and screenshots. Here the signing key sits in a config file that was committed.

// server/config.js
module.exports = {
  PORT: 3000,
  JWT_SECRET: "shelter2024",   // hardcoded
  JWT_ALG: "HS256"
};
03

Forge an admin token

Edit the payload, change role to admin, and sign it with the secret. HS256 uses the same key to sign and verify, so a leaked key means unlimited tokens.

FIX

What the audit report recommends

FindingRemediation
Hardcoded JWT secretLoad a long random secret from the environment or a secrets manager. Rotate it, and never commit it.
Role trusted from the tokenLook the user up server-side on each request and read the role from the database, not from the payload.
Long-lived tokensShort expiry plus refresh tokens that can be revoked.
Unprotected admin registrationAdmin accounts are created only by an authenticated admin. Ignore any role sent by the client.
Broken access controlCheck authorization on every route, deny by default, and test it with a normal user account.

Switch the server to Patched above, log in again, and repeat steps 3 and 4. The forged token is rejected because the real secret is random and never leaves the server.
